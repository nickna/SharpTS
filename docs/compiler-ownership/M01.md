# M01: Module declaration and export ownership

Resolves [#1894](https://github.com/nickna/SharpTS/issues/1894), including C04's transferred
namespace observation. Immediate inventory: `artifacts/epic-1865/M01-source.txt`.

| Stores | Owner, key and phase |
| --- | --- |
| `Types`, `ExportFields`, `InitMethods`, `_moduleGetNamespaceMethods` | One compiler's normalized-module-path maps. Module declaration creates type/export/init/namespace getter handles; bodies populate exports and namespace getters expose those same live fields. Init guards handle cycles/repeated imports. Types finalize after module bodies and entry-point initialization are emitted. |
| `ClassToModule`, `FunctionToModule`, `EnumToModule` | Legacy simple-name indexes for fallback lookup. Current module declarations and exact import/export owners take precedence. They do not independently own emitted handles. |
| `Namespaces`, `CurrentPath`, `CurrentDotNetNamespace`, resolver | Per-path directive configuration and current emission selection. The active namespace now reads the owning path's stored configuration, with the single-file/script setting as fallback. |
| `Names` / context `ModuleNames` | Protected path-keyed naming snapshot built from the complete graph before runtime/declaration emission. Consumers share it; standalone contexts retain filename fallback. |
| `ExportAssignmentClasses`, `ExportedClasses`, `DefaultExportClasses` | Exporting module path (plus export name for named exports) selects the qualified class identity. These are exact aliases to declarations, used by constructors and imported receiver dispatch. |
| `ImportFields`, `CommonJsExportFields`, `CommonJsGetExportsMethods` | Per-module import-name slots, CJS exports reference and getter handles. ESM live exports and CJS mutable export objects have different protocols; they intentionally retain separate views. |
| `CompilationContext.Modules` aliases | Module/namespace scope and shared declaration maps are selected by factories and import processing. Context-local import aliases are lexical bindings; contexts do not allocate a rival module type or export catalog. |

Two original failures are preserved: `M01-namespace-before` reports missing namespaced
property dispatch in both import orders; `M01-names-before` reports duplicate class dispatch
for distinct `left/index.ts` and `right/index.ts`. Namespace extraction previously affected
declaration only, then was cleared before later method phases. Filename prefixes were
also reused for class/function/enum declarations even though module type names already
had a collision fallback.

[`ModuleNameRegistry`](../../src/SharpTS/Compilation/ModuleNameRegistry.cs) allocates unique
sanitized prefixes in ordinal path order, reserving existing unambiguous names before adding
suffixes. Thus import order cannot choose a different owner, sanitized spellings also cannot
collide, and existing unique filenames retain their prefixes. Class/function/enum resolution,
module/script carriers and hosted binding names use the same snapshot. The definition context
refreshes its shared view rather than keeping a stale one.

Imported construction already had an exact export owner; an immediate method call on that
new value now reuses it rather than selecting the last same-named class in a global index.
Async-arrow collection likewise already records the qualified private owner; body emission
now consumes that identity without applying the current namespace a second time.

Module declarations must remain available before bodies for forward/cyclic references.
Namespace/export objects are runtime values and remain mutable where their protocol requires
it. The naming snapshot can complete early; generated type/field/method declaration cannot
complete until body consumers have finished. No general registry conversion is introduced.
